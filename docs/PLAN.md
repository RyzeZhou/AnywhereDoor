# 任意门 AWD（Anywhere Door）· 规划

> 状态：**P0 后端已写码**（2026-09-29：Awd.Core + Awd.CLI 完成，本机未编译；待 win10_vm 按 [TESTS.md](TESTS.md) 验证）
> 日期：2026-09-29 ｜ 缩写 **AWD**

## 一句话定位

**唤起即跳**：常驻托盘的小工具，按全局热键弹出输入框，到达任意
**本地目录 / 远程目录 / 网站 / 程序**。四类目标各占一页，每页独立收藏。

## 它的来历（这决定了它为什么长这样）

AWD 最早**不是独立软件**，而是**哆啦A梦百宝箱（TBX）内置的一个工具**：
当脚本有结果返回时，抓取返回的目录或文件，点击直接到达。**那个版本没有做出来。**

后来有了 ERF / US / FSY / TBX 这几件设计之后，它的用途变大了 ——
**从"TBX 的一个小工具"升级为整个系列的「到达层」**。

所以现在的 AWD 有两个身份，二者**共用同一套收藏数据**：

- **独立形态**：托盘常驻 + 全局热键 —— 不打开任何东西也能跳
- **集成形态**：将来作为统一文件管理器里的「快捷键直达」

## 与最终形态的关系

在系列的最终形态里，AWD 是**到达层**：

```
外壳层   统一文件管理器（本地 + 远程同一窗口、键鼠优先、紧凑）
 ├ 位置层  ILocation
 ├ 查找层  US（文件名 / 内容 / 文献库）
 ├ 搬运层  FSY + ERF
 ├ 动作层  TBX
 ├ 到达层  ← AWD 在这里
 └ 呈现层  程序启动台（AWD 与外壳共用同一套数据）
```

## 四类目标

| 页 | 目标形态 | 到达方式 |
|---|---|---|
| **本地** | 目录路径 | `explorer.exe` 打开 |
| **远程** | `站点:路径` | **交给 ERF**（`erf:` 协议），**不自己实现 SFTP** |
| **网站** | URL | 默认浏览器 |
| **程序** | exe / 快捷方式 / UWP | `Process.Start`；**UWP 走 `IApplicationActivationManager`** |

## 先做「程序」页（相对早期计划的调整）

原打算四页一起做，**现在决定「程序」页最先做**：

1. **它最独立** —— 不依赖 `ILocation` / ERF / FSY，纯本地
2. **它最痛** —— 现在用"桌面文件夹 + 中图标"凑合，做完立刻有收益
3. **最像"任意门"** —— 其余三页都有替代品，**只有应用网格是真空**
4. **能先验证"收藏 + 摆放"数据模型** —— 后面三页全部复用

### 程序启动台 = 手机式方块网格

Windows 在这个位置是**真空**：同类工具（Flow Launcher、PowerToys Run）全是**搜索式**，
**网格式没有**。两者不可互替 —— 搜索式考"记得名字"，网格式考"**视觉记忆 + 一次点击**"。

借"文件"语义的网格差在哪（Explorer 中图标 + 桌面文件夹）：

| 手机主屏有 | Explorer 中图标 |
|---|---|
| 自由摆放 | ❌ 必须自动排列 |
| 分页 / 分组 | ❌ 只能靠子文件夹 |
| 拖到一起自动成组 | ❌ 只能手动建 |
| 去扩展名、大图标为主 | △ 中图标 48px，名字带 `.lnk` |
| 长按出快速动作 | ❌ 那是"文件"的菜单 |
| 下拉即搜 | △ 对快捷方式不友好 |

### 四个关键实现点

1. **jumbo 图标**：`IShellItemImageFactory::GetImage` 拿 256px（Explorer 自己就这么做）；
   UWP 应用从 `shell:AppsFolder` 枚举。
   **先验证可得性** —— 有些老程序资源里只有 32px，那会影响视觉方案
   （可能统一放进圆角方块里，反而更整齐）
2. **启动分两类**：传统 exe / .lnk 用 `Process.Start`（**注意工作目录**）；
   **UWP 必须用 `IApplicationActivationManager::ActivateApplication`**
   （否则"商店应用点了没反应"，这是同类工具最常见的翻车点）
3. **虚拟化网格**：用 `VirtualizingWrapPanel`，别把几百个方块直接塞进 `WrapPanel`
4. **数据是"应用清单"不是"文件夹"**：
   `{名称, 目标(路径或AUMID), 图标缓存, 分组, 排序位置, 参数}`，存 JSON

## 形态

- **托盘常驻** + 全局热键 → 弹出输入框（**主入口，用完即走**）
- **主窗口**：只在整理收藏时打开

## 技术栈

- **.NET 8 + WPF**（与 ERF 客户端 / FSY / US 一致，人和经验都能复用）
- **全局热键**：`RegisterHotKey` + `HwndSource` + `WM_HOTKEY`
  （独立进程，没有 ERF 在 explorer 进程内那些限制）
- **托盘**：`NotifyIcon`（WinForms 互操作，ERF 有先例）
- **收藏持久化**：JSON，`%APPDATA%\AnywhereDoor\favorites.json`
- 原则：不联网、不常驻大内存、启动快

## 数据与存储（三份 JSON + 图标缓存）

| 位置 | 内容 | 要点 |
|---|---|---|
| `%APPDATA%\AnywhereDoor\favorites.json` | `{version, apps:[AppEntry…]}` | **四页混在一个数组里**，靠每条的 `page` 分页；随用户漫游 |
| `%APPDATA%\AnywhereDoor\groups.json` | `[{page, name, color}]` | 分组**登记表**，与条目分开存 —— 空分组也能存在 |
| `%APPDATA%\AnywhereDoor\settings.json` | `{doubleClickOpen, siteColors}` | 站点颜色记在任意门侧（站点清单属于易远传，只读） |
| `%LOCALAPPDATA%\AnywhereDoor\iconcache\<id>_<size>.png` | 图标缓存 | 机器本地，不漫游；`favorites.json` 里 `iconPath` 指过去 |

一条收藏的字段：`id`（`SHA256(target)` 前 8 位，天然去重）/ `name` / `kind` / `page` /
`target` / `arguments` / `workingDir` / `group` / `position` / `iconPath`。

- **分组不是容器，是条目上的一个字符串字段**（`group`）；null 或缺字段 = 未分类。
- **布局就只是 `position`**：每页各自 0 起连续，没有坐标与行列 —— 程序页 `WrapPanel` 按顺序流式排，
  窗口宽度一变排布跟着变。**口径两边必须一致**：CLI 早先是全局 0..N-1，已统一为页内（2026-10-01）。
- 侧栏显示的是"登记表名字 ∪ 条目里出现过的名字"，所以**只改条目的 `group` 就能凭空造出一个分组**
  （未登记，颜色中性）。
- 同一个"页"概念两套写法：`favorites.json` 里是字符串（`programs/local/web/remote`），
  `groups.json` 里是整数（`0/1/2`）—— 手改 JSON 时最容易错的地方。
- **"当前选中哪个分组"不落盘**（视图状态，每次启动回「全部」）；GUI 也**不监视文件**，
  CLI 改完要重启 GUI 才看得见（实测：改名后运行中的界面不变，重启立刻正确）。
- 颜色预设中英对照、GUI 与 CLI 共用一份（`Awd.Core/GroupPalette.cs`），**落盘永远是 `#RRGGBB`**。

## CLI 与 GUI 等效（2026-10-01）

`awd`（`src/Awd.CLI`）现在覆盖 GUI 的整理动作，且**无状态** —— 分组当参数用，跟目录那套逻辑一致：

```
awd group list|add|rename|remove|color <名称> [--page 程序|本地|网站|远程]
awd fav list [--page P] [--group G]        # --group - 只看未分类
awd fav group <id> <分组名|->              # = GUI 把条目拖到侧栏
awd fav add <目标> [--page P] [--kind K] [--group G]
awd fav move <id> <页内位置> | remove <id>
awd group color <名称> 蓝|blue|6|#0000FF   # 十项中英对照预设，见 help
```

不等效的只剩三处，都是"GUI 才有"的东西：**拖拽摆位与投放区**（鼠标手势）、
**书签导入**（GUI 窗口）、**站点颜色**（在 `settings.json`，CLI 暂未开命令）。

## 任意门地图（下一步的存储形态）

**用户要求（2026-10-01）**：布局要能**设置多个**并**各自存成文件**，这个文件叫**「任意门地图」**，
上面记载**四页各自的分组、条目、配色与顺序**；要用**更紧凑的格式**存储。

### 先量过：紧凑的空间在哪（7 条收藏 = 2128 字节）

| 字段 | 占比 | 判断 |
|---|---|---|
| `target` | 28% | 真数据，动不了 |
| `iconPath` | 28% | **纯派生**（缓存目录 + id + 尺寸）→ 不该进文件 |
| `name` | 8% | 真数据 |
| `page` | 7% | 可省：按页分组存，不必每条重复写 |
| `id` | 7% | **可推导**（`SHA256(target)` 前 8 位）→ 加载时现算 |
| `arguments` | 6% | 多数是空串；空串不是 null，所以 `WhenWritingNull` 没省掉它 |
| `kind` / `position` | 11% | 真数据，键名可缩短 |
| 缩进与括号 | ≈28% | 关掉 `WriteIndented` 即省 |

→ **不损失任何信息、也不上二进制的前提下，同一份数据能压到 1/3 左右**。
原则不变：文件是给人看、也可能给人手改的（`FavoritesStore` 里那条"中文别转 `\uXXXX`"同源），
所以紧凑靠**去派生字段 + 去缩进 + 短键名**，不靠编码技巧。

### 待定（动手前要拍板的五条）

1. **地图是否取代现有三份文件**成为唯一事实源（推荐：是 —— 否则"多套布局"退化成"多份备份"，
   切换即覆盖，还要防手滑丢数据）。`settings.json` 里的 `doubleClickOpen` 属于人的偏好，**不进地图**。
2. **格式**：紧凑 JSON（短键、不缩进、按页分组，复用 `System.Text.Json`）还是行式自定义
   （最省最好读，但要自己写解析与报错）。二进制不考虑 —— 直接违背"可手改"。
3. **分组自己的顺序**现在没处存（侧栏顺序 = 登记表顺序 + 未登记的追加）。地图要能定序就得**显式加排序字段**。
4. **坏文件不能再"静默当空"**：现在 `GroupStore.Load()` 的 `catch` 是返回空表，
   下一次 `Save()` 就把登记表**永久清空** —— 等于一次损坏丢光分组。地图化必须配**原子写**
   （写临时文件再替换，现在 `File.WriteAllText` 不是原子的）+ 读失败时保留原文件并报错，不许静默降级。
5. **同一条 `target` 能否出现在两页**：现在 GUI 只在页内查重，而 `id` 由 target 算、图标缓存按 id 命名 ——
   跨页重复会让 `@id` 引用有歧义。建议地图内**全局唯一**。

### 与已知风险的关系

上一轮记下"GUI 不监视文件、两边同时写 `favorites.json` 会互相覆盖"。地图化之后**一次只加载一张地图**，
切换是 GUI 内部动作，这个并发面反而收拢了 —— 但 CLI 改地图文件后仍需重启 GUI。
